# Implementation

## Realization map

| Concern | Realized behavior | Key paths / entry points | Non-obvious implementation fact |
|---|---|---|---|
| Shared provider connections | OpenAI, DashScope, and DeepSeek protocols, base URLs, base-URL override names, and API-key environment names load from one JSON authority. | `.ai/llm/providers.json`; `LlmConfigLoader.getProvider` | Persisted encrypted Literature secrets still win over environment-backed keys; the config owns which environment name is read. |
| Typed configuration loading | The loader validates providers, stable IDs, URLs, environment names, feature calls, prompt containment, native parameters, and tool arrays, then caches immutable call records. | `apps/backend/src/services/llm-config-loader.ts` | Prompt paths resolve relative to each feature directory and may not escape it. The default root is the repository `.ai/llm`; future packaged backends must supply/include the same application-root asset. |
| Provider execution | The gateway obtains endpoint and credential metadata from the loader while retaining protocol bodies, strict-schema normalization, retry, telemetry, pricing, and curl fallback. Native call parameters and tools are passed without remapping. | `apps/backend/src/services/llm-gateway.ts`; `apps/backend/src/app.ts` | The injectable curl command exists only to make the security fallback test platform-independent; production still invokes `curl`. |
| Literature model defaults | Embedding, extraction, and auto-pull shipped model/version defaults come from `literature-processing/config.json`; persisted profile selections and custom models still override shipped defaults. Bare retrieval/flow fallbacks and the Paper Implementation semantic-dimension compatibility check resolve the same configured embedding profile. | `.ai/llm/literature-processing/config.json`; `literature-llm-config.ts`; Literature acquisition/content-processing/retrieval/flow services | Legacy-model recognition remains code-owned migration behavior, not the current model authority. |
| Literature prompts and native parameters | Auto-pull scoring plus section extraction/consolidation load system prompts, provider-native parameters, and tools from feature config. Dynamic user payloads and output schemas remain in code. | `.ai/llm/literature-processing/prompts/**`; auto-pull ranking; key-content extraction service | OpenAI and DashScope entries are distinct so a persisted provider switch never receives another provider's native parameter shape. |
| Topic Selection and Paper Implementation model routes | Shipped provider IDs, model IDs, and provider-native overrides load from independent feature configs while profile purpose, timeouts, normalized portability parameters, capability policy, and eligibility remain code-owned. | `.ai/llm/topic-selection/config.json`; `.ai/llm/paper-implementation/config.json`; `topic-selection-model-profile-registry-service.ts` | The shared registry selects the feature config from the stable profile family. DeepSeek remains authored only for the eligible Topic Selection debate roles; Paper Implementation has no DeepSeek route. |
| Topic Selection v1a prompt family | N5 evidence extraction, N7 need adjudication, and N8 human-confirmation review system prompts load from a prompt catalog in the Topic Selection feature config. Dynamic user payloads and the diagnostic appendix stay in code. | `.ai/llm/topic-selection/prompts/v1a/**`; `topic-selection-v1a-llm-runtime-binding-service.ts` | Prompt catalog entries intentionally omit provider/model because runtime model selection is profile-driven. Existing golden hashes prove all three rendered system messages remain byte-identical. |
| Topic Selection v1b single-agent prompt families | N2/N3/N5 semantic support, N4 research-slice drafting, N6 candidate drafting/loopback triage, N7 support, and N8 value assessment load versioned system bodies from the Topic Selection prompt catalog. | `.ai/llm/topic-selection/prompts/v1b/**`; the six matching v1b runtime services | Decision-memory suffixes remain dynamic code composition. Existing per-slot golden hashes and byte-stability tests cover the external bodies and rendered prompt packets. |
| Topic Selection debate and v1c prompt families | v1b N6/N8 debate roles plus v1c N2 debate, N3 promotion support, N4 delegated decision, and N6 feedback normalization load static system bodies and versions from the prompt catalog. | `.ai/llm/topic-selection/prompts/v1b/**`; `.ai/llm/topic-selection/prompts/v1c/**`; matching runtime and gate services | Debate admission, role ordering, provider-path dormancy, dynamic user packets, compression, and authority boundaries remain code-owned and unchanged. |
| Topic Selection need/resource prompt families | Single-agent need drafting, four-role need-discovery debate, and resource-sampling classification load their versioned system bodies from Topic Selection config. | `.ai/llm/topic-selection/prompts/v1a/**`; `.ai/llm/topic-selection/prompts/resource-sampling/**`; matching production services | The debate scenario remains the compatibility contract and is checked against configured prompt versions. Provider-canary-only minimal messages remain inline diagnostic payloads, not production prompt authority. |
| Paper Implementation prompt families | Core-motive bootstrap, result analysis, experiment/route/validation/feasibility planning, cross/evidence boards, motive decomposition/evolution, P1 review, and trace-integrity debate load versioned prompt bodies from the Paper Implementation catalog. | `.ai/llm/paper-implementation/prompts/**`; `paper-implementation-prompt-config.ts`; matching runtime services | Shared prompt IDs/versions remain persisted compatibility contracts and are checked against config. Role/provider-specific dynamic appendices, strict schemas, admission, compression, resume, and artifact assembly remain code-owned. |
| Settings UI model labels | Model hints render only from backend-returned profiles; the renderer no longer carries stale shipped model names. | `LiteratureContentProcessingSettingsPanel.tsx` | This is a data-authority correction with no composition or styling change, so no HTML mock was required. |
| LLM runtime asset and CI contract | Repository-backed local/test/desktop backend execution treats `.ai/llm` as runtime data and fails fast when any provider, feature config, or prompt path is invalid. | `.ai/llm/AGENTS.md`; `README.md`; `pnpm llm:config:check`; `.github/workflows/ci.yml` | There is no standalone packaged backend today. A future package must include `.ai/llm` at its application root or supply an explicit loader root; absence is an error, never a hardcoded fallback. |
| UI change governance | Maintained guidance names the researcher job, consumed style authority, reuse order, icon status, accepted compatibility deviations, and the HTML mock gate for future non-trivial composition changes. | `AGENTS.md`; `docs/context/ui/current-state-alignment.md` | This task changes no layout or styling. Existing local inline SVGs are recorded as an accepted deviation because the repository has no canonical icon component or library contract yet. |
