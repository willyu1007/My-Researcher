# 02 Architecture

## Context and current state
- The upstream non-debate Topic Selection path and downstream PI/EF scientific path already exist and have separate real-run evidence.
- T-137 must connect them without becoming a new workflow framework or duplicating domain authority.
- PI and EF remain peer bounded contexts; each service resolves and owns its own persisted state.

## Proposed design
Use a thin semantic coordinator over existing product writers. It carries one small `ResearchIntent`, asks existing services for technical state, and derives the next incomplete action from persisted owner records.

```text
ResearchIntent
  → TopicDecision / PaperProject
  → ExperimentQuestion / WorkOrder
  → EF ScientificFacts
  → PI EvidenceSummary / Claim / Dossier
```

`ResearchIntent`, `ExperimentQuestion`, `EvidenceSummary`, and `LineageSummary` describe task-level semantic roles. T-137 should reuse existing domain artifacts that already express those roles rather than introduce parallel product schemas.

## Components
- **Semantic source selector**
  - Applies existing hard eligibility checks.
  - Uses LLM semantic comparison to select the best default source/topic and explain why.
  - Stops only when no candidate clears a minimum semantic threshold; optional human override is not a mandatory gate.
- **Thin coordinator**
  - Calls existing product routes/services in a fixed sequence.
  - Resolves state from existing owners; stores no second workflow truth.
  - Exposes one normal next action and bounded failure diagnostics.
- **Existing domain writers**
  - Topic Selection owns TopicDecision/Bridge.
  - PaperProject/PI own project intent, WorkOrder, evidence admission, interpretation, Closure, Claim, and Dossier.
  - EF owns Run/Attempt/Result/validation/EvidenceCandidate.
- **Semantic acceptance reader**
  - Re-resolves key authority anchors.
  - Produces a short `LineageSummary`; it is evidence, not authority.

## Validation policy

### Strict server validation
- Object exists, belongs to the expected project/scope, and is on the current accepted version/head.
- Scientific observations are generated by the EF-owned execution path.
- Paid provider Job creation and immutable scientific writers are idempotent.
- WorkOrder/Run/Result/Closure/Dossier authority hashes and claim ceilings remain valid.
- Real PAI execution stays within the one authorized cost/Job/credential window.

### Semantic LLM validation
- The selected literature is relevant to the research intent.
- The ExperimentQuestion is a genuine test of the promoted topic.
- Evidence interpretation reflects the server-provided scientific facts.
- Claim wording and strength follow from the evidence and constraints.

Do not repeat the same invariant at every stage. The owning service validates hard facts once; downstream stages consume its admitted result.

## Authorization policy
- Ordinary configured LLM calls use existing product model profiles and budget limits without new approval.
- Existing topic promotion authority remains part of the product path; T-137 adds no additional human sign-off.
- One explicit authorization is required immediately before temporary cloud credentials and real paid PAI execution.
- The compact `ExecutionPolicy` has four operator-visible values:
  - maximum paid Jobs
  - maximum cost
  - credential expiry
  - execution window
- Provider-specific payloads, ids, hashes, and derived capabilities remain server-owned.

## Resume model
The coordinator derives progress from existing persisted records; task labels are descriptive only:

```text
prepared
→ topic_promoted
→ paper_project_ready
→ experiment_ready
→ evidence_ready
→ dossier_ready
```

- Completed steps are read, not re-executed.
- Failed/incomplete steps expose one next action.
- Expensive-provider and immutable-writer commands remain idempotent.
- No new workflow-state table or general DAG is planned.

## Interfaces and data
- Use existing Literature, TitleCard, Topic Selection, PaperProject, PI, and EF routes/services.
- No new public API or Prisma migration is planned.
- A task-local coordinator is required because the current E2E runners embed fixture/P313/T132/T136 semantics. It accepts the fixed T-137 `ResearchIntent` plus existing source/project selectors, not a large bag of technical parameters.
- The coordinator has one fixed happy path and derives the next incomplete action by reading existing owner records. It does not expose a generic stage graph, mode matrix, or caller-authored authority payload.
- Its first implementation boundary ended after fresh Topic/PaperProject/PI/EF preflight state was composed and read back. The separately authorized real PAI and credential-free acceptance continuations are now complete.
- Technical refs/hashes are returned by owners and forwarded by code, never manually authored by the user or LLM.
- The implemented coordinator is `.ai/scripts/t137-scientific-dossier-canary.mjs`. It has exactly two pre-PAI stages: Topic/PaperProject and PI/EF preflight.
- `apps/backend/scripts/t137-scientific-dossier-canary-profile.ts` is the single task-owned semantic input. It fixes the four literature roles, question, metric, comparison direction, thresholds, fixed inputs, and prohibited claims.
- The Topic stage still uses the existing V1A and V1B WorkflowHarness writers. T-137 adds one named semantic mode, not a provider mode or configurable workflow.
- PI bootstrap, motive, evidence-board, validation, trace, and new WorkOrder admissions use existing HTTP product writers. The WorkOrder schema uses `work_order_schema_version` as a discriminant, so Fastify evaluates only the matching v1 or v2 shape and preserves executable v2 fields.
- The one historical T-137 WorkOrder row created before that fix is recovered by the canonical owner reader after exact branch/revision/cell comparison; a fresh missing admission always uses the HTTP writer. No repository row is authored directly by the coordinator.
- EF materialization uses the existing integration relay and shared active SciFact exact assets/readiness/execution bundle. Only the new T-137 Run authority is fresh.
- The real continuation has two commands rather than a configurable stage graph:
  - `t137:pai` owns temporary-credential validation, the two exact PAI Jobs, collection, server Result generation, scientific validation, and EvidenceCandidate→REU relay.
  - `t137:accept` refuses Alibaba credentials and owns configured ResultAnalysis, deterministic Closure/Packet materialization, Claim, Dossier, and final owner readback.
- Both commands offer `offline-preflight` and `execute`. Preflight is read-only; execute derives progress from persisted domain authority and reuses deterministic ids/business keys.
- Terminal state is credential-free: PAI preflight reports that scientific evidence was consumed by the closed Cycle, PAI execute rejects the closed Cycle before credential access, and acceptance replay reads the existing Packet/Claim/Dossier without requiring an LLM key.

## LineageSummary
The final summary contains:
- research goal and source-selection rationale
- Literature/TitleCard anchors
- Topic/PaperProject anchor
- ExperimentQuestion and WorkOrder anchor
- Run/Attempt/Result anchors
- EvidenceCandidate/REU anchor
- Closure/Dossier anchors
- concise evidence-to-claim explanation
- paid Job count, cleanup status, and capability resting state

It omits copied domain payloads, exhaustive table counts, prompt/cache internals, and unrelated intermediate hashes.

## Boundaries
- No cross-domain ORM cascade or new foreign key.
- No direct repository authority writes that bypass product writers; a domain service call is allowed where the HTTP adapter cannot represent the same valid v2 command.
- No caller-authored Result, conclusion, authority hash, or manual ref graft.
- No second evidence, Closure, Packet, Claim, or Dossier writer.
- No T-132/T-136 history reuse, provider debate, or persistent capability enablement.

## Rollout and recovery
- Task-local canary only; no traffic cutover.
- Stop before any unapproved external effect.
- On failure, clear temporary credentials, restore process-scoped capabilities, preserve accepted history, and resume from the latest owner record.
- A need for new schema/authority/API/UI/provider work stops this task for a scope decision.
